# src1.3.2 与 src1.3.3A：realcompetiton_2024 36 题全量对比

> 环境提示：本报告使用当时的默认 WSL（g++ 15.2），不是用户指定的
> Ubuntu 18.04 / 26env。指定环境下的正式结果见
> `test-results/realcompetition-src132-vs-src133A-all36-ubuntu1804-26env-20260922/report.md`。

## 测试协议

- 版本：`src1.3.2`（提交 `2ededf2`）与 `src1.3.3A`（提交 `7a5bff7`）。
- 环境：同一台机器、同一份本机 `NFSQ4.2` 真实 SDK；两版均重新以
  `g++ -std=c++11 -O2` 编译。
- 题集：`题目/realcompetiton_2024/01.xml` 至 `36.xml`，包括未列入旧
  `test.list` 的文件。
- 参数：Stage 2、IT 模式、平台限时 5000 ms；因 SDK 固定使用 7932 端口，
  两版串行运行。
- 分数取平台最终 `# Score`，最高按 1000 计；动作从 `server.log` 的规范动作流
  提取，比较动作名和参数，不把动作返回值混入动作本身。`AskLoc` / `Sense`
  返回值另行比较，以区分随机环境差异和客户端策略差异。

可用 `run_compare.py --run-label <唯一标签>` 重新构建、运行并生成
`comparison.json` / `comparison.csv`。
原始 SDK 运行目录和构建产物由 `.gitignore` 排除。

## 汇总结论

- `src1.3.2`：34 题正常完成，02 为平台输入解析失败，03 在完成动作后的
  `Fini` 阶段因堆损坏退出；无平台硬超时。
- `src1.3.3A`：35 题正常完成，仅 02 因题目 XML 本身存在不匹配结束标签而由
  平台拒绝；无平台硬超时。03 不再崩溃，正常完成并得到 426 分。
- 将“未产生分数”按 0 计，36 题单轮总分为 `19390 -> 20120`，增加 730；
  只统计两版均正常完成的 34 题为 `19390 -> 19694`，增加 304。
- 共同成功的 34 题中：15 题分数提高、16 题相同、3 题降低。该计数包含
  Stage 2 随机回答和时间效率分，不应单独用于判断策略优劣。

## 执行逻辑比较

共同成功的 34 题中有 20 题的完整动作序列逐项一致：
05、09–12、17、19–23、25–33。它们的合计分数变化仅为 `+20`；其中
10、11、17、19、21、28–30 的小幅加分来自相同动作下的平台耗时下降。

其余差异可完整归类：

1. **平台随机回答不同（10 题）**：06、07、08、13、14、15、16、18、24、35。
   两版在首个不同 `AskLoc` / `Sense` 返回之前动作前缀一致，后续分数不能作
   同输入 A/B 比较。例如 07 的第一次 `AskLoc(5)` 分别返回位置 6 和位置 2，
   08 的对象位置回答也不同。
2. **相同外部证据、受时间门控影响（01、34、36）**：01 和 34 中，1.3.2 的
   动作流是 1.3.3A 的严格前缀，1.3.3A 分别多完成 2 个和 1 个目标。36 中，
   两版前 30 个动作一致；1.3.2 到 task 24 时只剩 690 ms，低于
   `440 ms 计划 + 300 ms 安全余量`，因此跳过并执行较短 pickup；1.3.3A
   当时剩 874 ms，按同一 legacy 顺序执行 task 24，多完成 6 个目标，随后因
   余量不足停止。差异来自墙钟时间进入既有 Deadline gate，不是 Candidate 排序改变。
3. **非法输入的预期安全恢复（03、04）**：03 中 1.3.2 已执行 Move/PickUp，
   但在 `Fini` 报 `free(): invalid next size (normal)` 并以 `SIGABRT` 退出；
   1.3.3A 完成同一目标并安全退出。04 的 instruction 缺少多处右括号；1.3.2
   将后续内容吞入首个 give，1.3.3A 隔离四个 malformed form，并从后续 marker
   恢复最后一个可解析的 takeout。两版该题均为 0 分，但 1.3.3A 的行为符合
   “局部非法 instruction 隔离、继续处理其他任务”的设计。
4. **平台无法建立题目（02）**：SDK 报 `Error reading end tag`，两版都在执行前
   得 0 分。此项不属于客户端回归。

静态核对中，`candidate_plan.cpp` 与 `candidate_plan.hpp` 在两版间 SHA-256
完全一致。结合动作流可判定：本轮未发现正常题的 Candidate 排序或执行策略被
安全层修改；可观察差异来自随机证据、非法输入恢复和原有时间预算门控。
