# 概率模型 #

当前对环境的判断
→ 估计各任务/动作的风险与收益
→ 选择动作
→ 收到真实的成功、失败、AskLoc 或 Sense 反馈
→ 更新后验
→ 用新的风险重新规划

# 出题小巧思 #

设计一类**对语义一致性要求很高、无法靠两个错误互相抵消蒙混过去的题**。

你这次 `1.6.2` 已经给出了一个很好的思路：以前有些实现虽然内部评分是错的，但因为 planner 的门控也“恰好错在另一个方向”，最后反而能得到不错的官方分数。这种补偿性耦合一旦换一个场景，往往会瞬间失效。   RELEASE_1.6.2

而且这类题完全可以做成**规则内、合法、可解释**的题，而不是靠格式错误或平台 bug。2026 规则明确要求同一道题不出现重复任务、重复约束，同时第二阶段允许初始状态和用户回答出错；评分又明确依赖终止状态、约束全过程保持和动作成本。    rules-2026     rules-2026

我会把这种出题方法叫做：

> **“破补偿性耦合题”**

最有效的不是把题搞得特别复杂，而是让两个错误在同一题里**不再同方向抵消，而是朝相反方向放大**。

比如你现在已经知道几类很适合做文章的语义轴。

第一类是 **“当前真值”和“历史计分资格”分离**。
可以设计一个约束：

- 初始满足；
- 中途因为某个高收益动作被破坏；
- 后面又恢复；
- 最终状态重新满足。

正确评分逻辑应该记住：这个约束已经失去维护资格，不会因为最后恢复而重新拿回约束分。规则也明确说约束必须从初始到终止中间每一步都满足。    rules-2026

这就可以一次性打掉两种常见错误：

- 只看终态的实现；
- “当前谓词恢复 → 约束分恢复”的实现。

而有趣的是，如果某个 planner 同时还错误地高估这条约束，它平时可能正好因此敢去做更多任务；这种题就能让这种“错误评分 + 激进策略”的组合真正付出代价。

第二类是 **`inside` 和 `at` 的分离**。
出题指南明确把小物体的 `at` 和 `inside` 作为两种不同状态；`info(on/near)` 对应 `at`，`info(inside)` 对应 `inside`。    2025中国机器人大赛服务机器人仿真项目出题指南      2025中国机器人大赛服务机器人仿真项目出题指南 

所以可以设计这样的链：

- 某物体在容器内；
- 容器在某地点；
- 同时给另一个任务/约束依赖该物体是否真的具有 `at`；
- 让“inside ⇒ at”的错误推导导致计划选择发生改变。

这种题特别好，因为它不是“很偏门的格式陷阱”，而是在测试 world model 是否把**关系语义**真的建对了。

第三类是 **失败动作后的状态与成本**。
规则明确：

- 物理动作成功才改变状态；
- 失败则状态不变；
- 但动作无论成功失败都扣分。    rules-2026     rules-2026

而第二阶段又允许初始状态错误。    rules-2026

这意味着你完全可以设计一个 Stage 2 题：

- 错误初始信息诱导一个“看起来可执行”的动作；
- 正确程序尝试后发现失败；
- 必须重新规划；
- 错误程序如果“失败也更新状态”、或者“不扣失败成本”、或者“不利用反馈”，都会开始偏离。

这种题对“AI 修补式代码”杀伤力很大，因为这种代码最容易出现局部 patch：修了 planner，却没同步 simulator；修了 simulator，却没同步 score bookkeeping；修了 feedback，却没同步 execution record。

第四类是 **低估和高估反转题**。
这是最像你说的 A/B bug coupling 的。

假设你知道某类程序：

- scorer 会高估计划 A；
- planner 会过度保守；
- 两个错误刚好抵消。

那你可以专门构造一个姐妹题，让：

- A 的真实收益降低；
- 但错误 scorer 仍然高估；
- planner 的保守机制恰好不再能兜底。

这样两个 bug 不再抵消，而是叠加。

这比单独做一个“大难题”更有价值，因为它是在测：

> 这个系统到底理解了规则，还是只是对某一类训练样题拟合得不错。

我尤其建议你采用**成对题设计**。

例如同一个基础场景，只改变一个变量：

- 题 A：物体 `at table`
- 题 B：物体 `inside cupboard`

或者：

- 题 A：约束始终没有被破坏
- 题 B：中途破坏后恢复

或者：

- 题 A：动作成功
- 题 B：通过 Stage 2 `err/mis` 让第一次动作失败

其他内容尽量保持一致。

这样如果某个程序 A 得分正常、B 突然崩掉，你几乎可以直接推断：

> 它依赖的是某个错误假设，而不是一般性的规划能力。

这其实已经有点像软件测试里的 **metamorphic testing（蜕变测试）**：不是只问“这道题答案是多少”，而是问：

> 我只改了一个具有明确语义的条件，你的行为是否发生了合理的变化？

对 RoboCup 这种黑盒执行程序，这种方法特别合适。

不过有一条边界我建议你守住：**不要把题做成依赖未文档化 grader quirks 的题。**

比如你现在 `1.6.2` 报告里还有：

- ASP 首个 answer set 的 binding 顺序；
- 某些条件语法；
- Stage 2 完整 `at/inside` 状态；
- UNKNOWN binding。

这些你自己都还没有完全等价复现。   RELEASE_1.6.2

这种东西适合拿来做你们自己的 fuzz/regression 测试，但暂时不适合作为“针对别人程序”的正式出题核心。否则最后测出来的可能不是“谁理解规则更好”，而是“谁恰好撞对了平台实现”。

所以我会把你们的出题目标总结成一句话：

> **不要出“怪题”，要出“反错误假设题”。**

如果要真正系统化，我甚至建议你们现在建立一个 **Bug → Assumption → Breaker Question** 表。

比如：

| 错误假设             | 平时为什么可能没事   | Breaker 题                   |
| -------------------- | -------------------- | ---------------------------- |
| `inside ⇒ at`        | 大多数目标恰好不区分 | 容器内物体同时参与位置目标   |
| 约束恢复后重新得分   | 常规路径不破坏约束   | 中途破坏后恢复               |
| 失败动作也更新状态   | Stage 1 很少失败     | Stage 2 错误初始信息诱发失败 |
| UNKNOWN 当作确定失败 | 乐观 scorer 曾经补偿 | 高价值但证据不完整的任务     |
| scorer 高估          | planner 偏保守抵消   | 让被高估方案真实代价变高     |
| 只看最终状态         | 很多题无中间约束变化 | 必须暂时破坏约束才能完成任务 |

我觉得这会是你们今年出题非常有竞争力的一条路线：**题目表面不一定难，但专门破坏“错误实现之间的偶然平衡”。**
