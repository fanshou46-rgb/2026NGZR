# 1.6.7 强化可行性与实施计划

日期：2026-10-05。状态：H1 已实施为独立 1.6.7.1 候选，完整综合 200 题对照已完成；正常行为/基础分保持一致，专项退出保护通过，未证明提分。H2–H6 待后续实施。见 [1.6.7.1 发布报告](../src1.6.7.1/docs/RELEASE_1.6.7.1.md)。

本计划以 `HistoryVersion/src1.6.7` 的原版 300ms 安全余量版本为主基线，以 `src1.6.7-200ms` 为辅助对照。目标是在保留其任务推进能力的基础上，改善事实判断、失败恢复、执行稳定性和完整路线效率。每轮只纳入一个可归因的改动；跨状态写入、查询和投影的语义修复，以一个完整闭环作为一轮。

## 二、六条开发经验

1. **正确判断与可执行路径必须一起建设。** 把错误的“已完成”改为“未知”后，要提供取得证据并完成任务的路线。1.7.4 的部分下降来自验证路径缺失。
2. **失败反馈需要条件解释。** Open 失败不能单独证明门已开；须排除手占用、地点和类型等其它原因。AskLoc 是线索，真实动作和感知决定后续确认。
3. **收益按最终状态计算。** 为放入而开门、为运输而离开终点，都可能需要恢复动作。恢复目标与恢复历史约束信用是两回事。
4. **探索服务于未完成任务。** 先执行已有可推进任务，停滞后再投入有限探索，预算覆盖发现后的完成路线与必要回程。
5. **搜索可复现性属于比赛能力。** 完整候选、稳定顺序、工作量限制和墙钟保护要配合，不能让机器负载决定是否漏掉关键任务。
6. **单元检查、SDK 语义、比赛收益分别验收。** 内部测试通过、目标增加或单个题提分，都不能单独判定强化成功。

## 三、范围与可行性

主线保留 1.6.7 的普通任务排序、必要感知、MustChooseOne、既有约束交换和 Multi-GOTO 能力。修复触及这些路径时，先建立原行为对照。原版已有 canonical 查询、StateMutation 异常恢复、失败纠错和局部查询优化；优先补缺口，避免重复建立同类系统。

| 阶段 | 工作包 | 预计收益性质 | 改动面 / 风险 | 实施建议 |
|---|---|---|---|---|
| H0 | 基线冻结与逐题诊断 | 提高归因与回退可靠性 | 小 / 低 | 必做 |
| H1 | 规划线程退出保护 | 防止清理与规划并发访问 | 中 / 中 | 第一项代码候选 |
| H2a | 有条件的失败学习与证据相关重试 | 减少错误确认、重复无效动作 | 中 / 中 | 小反例通过后推进 |
| H2b | 地点、柜内、手和托盘语义闭环 | 修复错误完成判断与多柜处理 | 大 / 高 | 独立完整工作包 |
| H3 | 完整路线及终态恢复 | 提高完成率、减少往返 | 中至大 / 中高 | 先做确定信息场景 |
| H4 | 停滞后的有界恢复探索 | 补救缺位置和错误线索 | 中 / 中高 | 最后进入策略试验 |
| H5 | 搜索稳定性与预算改进 | 降低运行波动、漏算和超时 | 中 / 中 | 诊断贯穿全程，改动独立验证 |
| H6 | 留出验证与发布选择 | 选出可用于比赛的子集 | 测试量大 / 低代码风险 | 达标工作包才组合 |

风险等级按依赖范围和行为影响估计，不是工期承诺。H2b 可能需要修改状态表示、事务回滚、查询、动作封装和投影，不能按“复制几个函数”估算。H1 可以形成独立候选；H2b 未通过时，其它试验仅在已证明语义成立的范围推进。

## 四、逐项实施方案

### H0：冻结基线，先定位 1.6.7 自己的问题

- 记录两个基线的源码、二进制、编译参数、官方 SDK、题目清单、种子和词表哈希；明确默认运行模式与 guarded 辅助模式。
- 复用已有结果解析和官方终态提取工具，统一 G（目标）、C（约束信用）、K（动作成本）、B（基础分）、F（封顶正式分）。
- 在失败题记录首次关键分叉、未完成目标、停止原因、剩余时间、近期动作结果和相关证据。停止原因区分无候选、事实未知、净收益不足、重试限制、搜索预算、动作期限与异常。
- 对后续版本暴露的问题，先在 1.6.7 上运行最小 SDK 反例。源码相似用于定位，反例实测用于确认。
- 诊断采样与正式计分分开；正式计分关闭重型日志和阶段计时，先测记录机制的行为影响。

交付：冻结清单、基线结果、按收益影响排序的问题清单。门槛：所有预期运行格都有状态；缺失和失败明确记录；能从原始日志重算官方指标。

### H1：退出保护，先解决清理时序

线索：1.7.2 增加 `planner_shutdown_requested` 和生命周期互斥，`Fini()` 先请求停止，再等待规划退出。1.6.7 尚无对应保护。需要在原版上验证 SDK 超时与清理交错的实际风险。

实施入口：`rdfw.hpp`、`rdfw.cpp` 中 Plan、SDK 调用包装、Fini 和析构相关路径。借鉴后续实现，先确认官方 SDK 的线程调用关系、锁顺序和在途调用可结束条件。

验证覆盖：正常结束、期限触发、SDK 调用异常、正在计算或调用期间清理、重复初始化与清理。检查无数据竞争导致的失效访问、无死锁、停止后无新增 SDK 调用、费用与反馈仍记一次。

通过条件：正常路径动作及 G/C/K/B 保持基线；故障交错反例通过；结束延迟、SDK 截止与外部超时单列。SDK 自身阻塞时的退出能力必须按实际接口说明，不以取消标记代替中断保证。

### H2a：失败证据与重试资格

线索：1.6.7 已有 `HoldSmallObject`、`GetSmallObjectStatus`、`TakeOutLogic` 等纠错链。当前应核查具体失败分支，而不是统一增加重试次数。

实施规则：

1. 把动作失败的可能原因与已确认前提逐项对应；仅在其它原因排除后产生负证据。
2. 按对象、地点或容器、动作、失败原因和相关事实保存已尝试路径。无关的 world revision 变化不能重置限额。
3. 新的相关感知或动作证据允许一次有边界的新尝试；相同弱回答不视为进展。新询问线索可以生成验证候选，但不能直接变成已确认事实。
4. 每次失败仍计入动作费用、时间及全题限额；避免各局部限额叠加成无界循环。

用例：错误地点反复回答、关闭容器内物品未被看到、未知手状态下 Open 失败、确认空手时 FromPlate 失败、新证据纠正错误容器、相关与无关状态变化对重试的影响。

通过条件：原成功纠错路径继续成功；失败因果符合 SDK；同证据无效重复下降；正常题 G/B/F 不出现稳定退化。

### H2b：关系和终态判断的完整修复

源码线索：1.6.7 的 `SenseCurrentLocationOnly` 只保留一个感知柜编号；PickUp 等路径调用 `ClearContainerMembership`；部分终态把柜内关系作为槽位排除依据。后续 SDK 反例表明这些假设需要逐项核实。

按以下依赖顺序完成一个语义闭环：

1. 地点显式 at、感知可见位置、逐容器 inside、手、托盘分开表达。多条 inside 使用逐边真／假／未知及来源；兼容字段只作派生视图，权威读取统一。
2. 每种动作只改 SDK 实际改变的字段与关系。PutIn/TakeOut 按指定边处理；其它关系和另一槽位依规则保留。
3. Sense 保留可见性歧义，处理同地多个容器；关闭容器内不可见不等于物品不存在；看见物品不能单独排除手持或托盘。
4. 同步 canonical 查询、终态判定、事务提交与回滚、派生事实失效、dry-run 投影和缓存。
5. 完成判断变成 UNKNOWN 的路径，补上必要且有预算的验证动作，核算验证后任务完成的完整代价。

实施入口：`rdfw.hpp/cpp`、`canonical_state.cpp`、`state_mutation.cpp`、`terminal_checker.cpp`，以及候选投影中的相关路径。参考 1.7.5—1.7.7 的语义反例和修复，不整体引入其调度器。

通过条件：所有最小反例的官方终态与内部确定判断一致；不出现错误确认；异常回滚完整；普通题保留有效完成路径。若只是内部完成数下降，应追踪官方 G，而不是恢复错误事实；若真实 G 也下降，须补执行路径后再发布。

### H3：完整路线与恢复动作

先处理事实已确认、能构造确定性动作路线的场景：放入后恢复 Close、运输后恢复 GOTO、先完成搬运再最终持物。先证明 1.6.7 在该场景确有遗漏，再添加候选。

方案：保留原候选，同时增加短小的完整路线；按最终目标、永久约束账本、全部动作成本和剩余时间比较。需要恢复才能盈利的前缀与恢复路线绑定。执行得到新反馈后重新检查计划；暂时目标下降不应单独触发对已验证恢复路线的放弃。

保留已有约束交换能力，记分约束的收益取舍按官方口径计算；物理前提与 SDK 动作合法性单独检查。关闭柜门可恢复关闭目标，不能恢复已经违反的“禁止打开”历史信用。

通过条件：有／无恢复时间、有／无冲突目标、有／无历史约束损失分别验证。最小反例净增目标或等目标降成本；正常题未因优先持物、抢先 GOTO 或过严筛选停滞。a04 只提供方向依据，收益由强化候选重新验证。

### H4：停滞后的有界恢复探索

触发点：普通任务、原纠错流程和原有可盈利组合都无法推进，且仍有完成后续任务的时间。先检查等待证据的是哪个目标及哪条事实。

第一版只增加少量有明确任务关联的候选：当前位置有效 Sense、已有公开地点线索的 Move+Sense、必要 AskLoc 后的验证。开柜探索等更复杂分支单独作为后续工作包。

探索成本、失败费用、当前目标损失、历史约束损失、后续搬运和回程共同进入估价。第一版对无法界定的收益和不可恢复损失保持拒绝。一次反馈后重新规划；同证据重复 Sense 不计进展。次数、费用和期限上限从开发集冻结，明确为工程参数。

通过条件：既有无法推进的反例得到真实 SDK 目标收益；信息无收益时及时停止；普通正收益任务不被探索延迟；所有新增感知能追溯到具体证据需求。

### H5：稳定搜索与时间预算

先在真实会执行的 1.6.7 路径定位预算分叉。guarded 专属改动必须单列，不能以其夹具收益宣称默认模式改善。

候选方向：固定平票顺序与节点工作配额；保留预算截止前完整验证的候选；分块检查昂贵循环；区分 SDK 等待、规划、反馈处理和日志开销。相同公开历史、时间输入和工作配额应给出一致决策。真实墙钟继续保护总期限。

缓存只用于已经证明等价的重复查询，键覆盖相关事实、证据资格及约束账本；状态变化后可靠失效。先对照缓存开关验证结果一致，再评价耗时。

300ms 主基线参数先固定。200ms 作为单独实验臂，禁止与语义、探索或排序改动捆绑。任何省略 Sense 的提案都须证明其反馈不会改变当前决策或后续必要证据，并通过不同隐藏状态的配对反例。

通过条件：固定输入离线重放 100% 一致；真实重复 G/C/K 一致率至少 99%，且不低于同期基线；超额、硬截止和尾部行为分叉逐条保留。搜索预算调整须同时检查长任务覆盖率。

## 五、验证分层与成本控制

### 每个工作包的四级验证

| 层级 | 范围 | 进入下一层的条件 |
|---|---|---|
| T0 | 原有相关测试、SDK 最小反例、异常／回滚检查 | 修复前能复现，修复后按预期改变；无相关旧回归失败 |
| T1 | 约 16—24 个定向输入，覆盖受影响路径和相邻反例 | 官方语义通过，收益机制可解释，所有退化已定位 |
| T2 | 冻结历史 71 输入、已有 90 合法题、52 结构题，按清单去重与分组 | 目标、基础分、正式分、时间与稳定性同时满足门槛 |
| T3 | 最终候选冻结后新建并冻结的独立留出题 | 正式分稳定提升，目标／基础分不退化，发布条件通过 |

T1 可用 IT/NT、一个固定种子加一次重复、基线与候选两臂，约 128—192 次 SDK 运行。失败优先在 T0/T1 定位，避免每次修改都跑全矩阵。

T2/T3 使用三个独立种子，加首种子重复；同题同种子串行轮换 AB/BA。重复轮只测波动。若 T2 冻结后恰有 213 个输入，两臂为 3408 次 SDK 运行；最终加入 200ms 辅助臂则为 5112 次。实际数量以清单有效输入与去重结果为准。普通比赛、结构压力、Stage 1/2 分组统计，不混成一个排名。

正式计分期间保持机器负载稳定，避免并行编译、归档和 Git 打包。Windows/WSL 入口保存路径、编译器与 SDK 版本；词表使用经核对的临时 LF 副本，原题和 SDK 保持原字节。

### 指标与统计口径

- 以 SDK 官方终态提取 G/C；K 按所有已尝试动作重算。基础分 `B = 40G + 20·I(G>0)·C − K`，零目标时的约束加分条件必须保留。
- 同时保存 SDK 原始分、逐题封顶后的 F、平台耗时、失败动作、SDK 硬截止、外部超时及缺失状态。
- 内部完成计数仅用于诊断。缺失 G/B 保持缺失，另报告正式分缺失按零的保守汇总；有评分的超时仍标记超时。
- 留出集按独立题族聚类估计配对差值的 95% 区间，IT/NT、多种子和排列变体保持同一题族相关性。平均 F 改善区间下界须大于 0，G/B 的下界须不小于 0。
- 点估计上升但区间跨 0 时，结论为证据不足；先检查效果与波动，再决定扩充新题族。已用于修改参数的题转入回归集。

### 采用与回退规则

1. **稳定性保护包：** 普通路径动作和 G/C/K/B 原则上等价；时间取整差单列。故障路径按修复目标验收，不把故障注入后的停止行为混入正常成绩。
2. **语义修复包：** 已确认 SDK 反例必须修复；普通任务完成路径也需通过。若修复导致真实目标明显下降，候选继续开发，比赛基线保持冻结。
3. **策略收益包：** T2 各主要题组 G/B/F 点估计不下降；确定、重复出现的目标损失须解决或采用有证据的通用适用条件隔离。需要新增比赛取舍政策的方案另立提案。
4. **最终发布：** T3 区间门槛、重复一致率、语义检查全部通过；无新增可复现崩溃、死锁和截止缺陷。任何已观察退化都随报告交付。
5. **回退方式：** 回到最后通过的独立版本和对应二进制；失败候选、日志与题目保留。每次修正使用新的结果目录，复跑不替换原失败格。
